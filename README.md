# LoanWise — loan eligibility guidance

A Flask application that estimates whether a loan application is likely to be
approved, **explains why**, and shows **what would change the answer**.

It is built to be honest about what it knows. The model is trained on a public
dataset of 614 historical applications; every number the interface shows comes
with the accuracy it was measured at, and the limitations are on a user-facing
page rather than buried in a footnote.

## What it actually does

| | |
|---|---|
| **Calibrated estimate** | A probability, not a verdict. Calibration is measured and published, so "72%" is a claim the model can back. |
| **Reasons** | Every result breaks down which of the applicant's answers moved the estimate, and by how much. |
| **Guidance** | Realistic changes — borrow less, extend the term, add a co-applicant, clear an arrear — re-scored through the same model, ranked by effect. |
| **Affordability** | Instalment, interest, and the largest loan the applicant can comfortably service, from a published amortisation formula. |
| **History** | Optional account to save scenarios and re-run them with one field changed. |
| **Analyst view** | Aggregate outcome mix, model version in service, and a JSON stats endpoint. |
| **JSON API** | The web UI is a client of it. Anonymous assessment needs no account and no token. |

**It is not a loan offer and not a credit decision.** No lender sees the input
and none is bound by the output.

## Current model performance

Regenerated by every training run into [`docs/MODEL.md`](docs/MODEL.md) — nothing
here is typed by hand.

| Metric | Value | Context |
|---|---|---|
| Holdout ROC-AUC | **0.803** | 0.5 is a coin flip |
| Cross-validated ROC-AUC | **0.728 ± 0.054** | the spread is the honest number |
| Brier score | **0.170** | 0.25 = always guessing 50% |
| Accuracy @ 0.65 | **0.797** | vs. a 68.7% always-approve baseline |
| Monotonic in loan amount | **yes** (0/216 reversals) | required for the guidance feature |

614 rows is a small dataset. This is a well-engineered demonstration of a
calibrated, explainable decisioning service — not a model validated for real
credit underwriting, and it does not claim to be.

## Quick start

```bash
git clone https://github.com/aaron-seq/Loan-eligibility-calculator.git
cd Loan-eligibility-calculator

python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

cp .env.example .env        # defaults are fine for local development
make train                  # ~30s — trains the model and regenerates docs/MODEL.md
make run                    # http://127.0.0.1:5000
```

A trained bundle is committed, so `make train` is optional for a first look. Run
it if you change anything in `loanapp/features.py` — the app refuses to serve a
model whose feature contract disagrees with the code.

To create an administrator (there is **no** default account and no default
password):

```bash
FLASK_ENV=development flask --app app create-admin \
  --user-id yourname --email you@example.com
```

## Using the API

Anonymous assessment works with plain `curl` — no account, no CSRF token:

```bash
curl -s localhost:5000/api/assess -H 'Content-Type: application/json' -d '{
  "applicant_income": 50000,
  "coapplicant_income": 10000,
  "loan_amount": 1500000,
  "loan_term_months": 240,
  "credit_history": 1,
  "dependents": 1,
  "education": "graduate",
  "property_area": "urban",
  "cibil_score": 730
}' | python -m json.tool
```

Full endpoint reference and response contracts: [`docs/API.md`](docs/API.md).

## Project layout

```
loanapp/
  features.py      Feature contract — the single source of truth for training AND serving
  rules.py         Deterministic affordability and credit checks
  explain.py       Factor attribution and what-if guidance
  assessment.py    Combines model + rules + explanation into one result
  schemas.py       Request validation (pydantic v2)
  security.py      CSRF, rate limiting, password hashing, auth decorators
  config.py        Environment config that fails closed in production
  db.py            SQLite schema and repositories
  ml/
    registry.py    Model bundle persistence + the feature-contract guard
    train.py       Training, evaluation, calibration, model card generation
  blueprints/      pages (HTML) · auth · api (JSON) · admin
templates/         Jinja templates
data/              train.csv, test.csv
models/            Committed model bundle + metrics.json
notebooks/         Original exploratory analysis, kept for provenance
docs/              ARCHITECTURE · MODEL (generated) · DEPLOYMENT · API · ROADMAP
```

## How the pieces fit together

```
HTTP request
   ↓  schemas.py          validate shape and range → LoanApplication
   ↓  features.py         engineer the model input (same code as training)
   ↓  ml/registry.py      pipeline, verified against the feature contract at load
   ↓  assessment.py       probability + rules + factors + guidance
   ↓  blueprints/         render HTML or JSON
```

The single most important line in that diagram is `features.py`. Training and
serving import the same function, so they cannot drift. Details and the
reasoning behind each layer: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Deployment

**Recommended: a container.** The application is stateful — accounts, saved
applications, an admin view — and containers give it a real filesystem.

```bash
docker build -t loanwise .
docker run -p 8000:8000 \
  -e SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')" \
  -v loanwise-data:/data \
  loanwise
```

**Serverless is not a supported target.** `vercel.json` was removed: the
filesystem is read-only outside `/tmp`, `/tmp` is destroyed on every cold
start, and it is not shared between concurrent instances — so accounts and
saved applications cannot survive. Anonymous assessment would work, but
shipping a config that silently loses user data is worse than not shipping one.
The app still detects a serverless environment and warns, for anyone who
deploys there deliberately. Full discussion and the migration path to Postgres:
[`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).

## Security

| | |
|---|---|
| Secrets | `SECRET_KEY` is required in production; the app refuses to start without it |
| Passwords | Werkzeug scrypt, per-hash salt, 12-character minimum |
| Sessions | HttpOnly, Secure by default in production, SameSite, 1-hour lifetime, rotated on login |
| CSRF | Enforced on every state-changing request that carries a session cookie |
| Rate limiting | Per-IP on login, registration and assessment |
| Access control | Ownership enforced in SQL; a missing record and someone else's are indistinguishable |
| Admin | Created by CLI only — no default account, no default password |
| Fair lending | Gender and marital status are neither collected nor used |

Dependencies are pinned exactly and audited with `pip-audit` in CI, weekly as
well as on every pull request. That job is not decoration — it caught 15
published advisories in an earlier pin set for this rewrite.

Known limitation, stated plainly: rate-limit counters live in process memory, so
N workers permit roughly N× the configured limit. Adequate against casual abuse,
not a substitute for a shared store or an edge WAF. See
[`docs/ROADMAP.md`](docs/ROADMAP.md).

## Development

Requires Python 3.11 or newer — the floor is set by numpy 2.4, pandas 3.0 and
scikit-learn 1.9, which all declare `requires-python >=3.11`.

```bash
make test       # pytest + coverage (currently 86%)
make lint       # ruff check + format check
make typecheck  # mypy --strict across the package
make audit      # pip-audit (dependency CVEs) + bandit (static scan)
make check      # all of the above — what CI runs
make train      # retrain and regenerate the model card
```

CI runs the suite on Python 3.11/3.12/3.13, audits dependencies against the PyPI
advisory database (weekly as well as per-PR), retrains the model from scratch,
and **fails** if the retrained model is non-monotonic, drops below a 0.70
ROC-AUC floor, or disagrees with the committed contracts.

## Contributing

Issues and pull requests are welcome. Two conventions worth knowing:

1. **Changing `FEATURE_COLUMNS`, or upgrading scikit-learn or numpy, requires a
   retrain.** The bundle records both the feature list and the library versions
   it was pickled under, and the app refuses to serve a mismatch rather than
   failing at request time. `make train` and commit the new bundle.
2. **Do not hand-edit `docs/MODEL.md`.** It is generated by the training run so
   that documented numbers always come from a real run.
